# 1. MISSÃO

Criar e manter uma arquitetura de internacionalização robusta.

O sistema deve permitir:

* interface totalmente localizada;
* alteração imediata de idioma;
* tradução entre os três idiomas;
* tradução de mensagens;
* tradução de voz;
* tradução de imagens;
* tradução de ficheiros;
* tradução através do Chat IA;
* deteção de idioma;
* correção linguística;
* preservação do significado original.

A regra mais importante é:

> **Traduzir não significa alterar a intenção do utilizador.**

Nunca tornar uma mensagem mais formal, agressiva, simpática ou técnica sem que isso tenha sido pedido.

---

# 2. IDIOMAS OFICIAIS

O TranslatorX suporta oficialmente:

```text
pt
en
pl
```

Correspondência:

```text
pt = Português
en = English
pl = Polski
```

Os idiomas devem possuir:

```text
src/i18n/pt.json
src/i18n/en.json
src/i18n/pl.json
```

Se a arquitetura existente utilizar outra organização equivalente, respeita a estrutura definida pelo Architect.

---

# 3. INTERFACE LANGUAGE VS COMMUNICATION LANGUAGE

São conceitos diferentes.

## Interface Language

Idioma usado para:

* menus;
* botões;
* labels;
* mensagens do sistema;
* configurações;
* onboarding;
* notificações;
* erros;
* estados da aplicação.

## My Language

Idioma que o utilizador normalmente fala/escreve.

## Other Person Language

Idioma da outra pessoa com quem comunica.

Estas configurações não devem ser confundidas.

Exemplo:

```text
Interface: Português
My language: Português
Other person: Polski
```

O utilizador vê a aplicação em português, mas comunica com a outra pessoa em polaco.

---

# 4. LANGUAGE OBJECT

Sempre que necessário, utilizar uma estrutura consistente:

```ts
type SupportedLanguage = "pt" | "en" | "pl";
```

Não utilizar strings arbitrárias espalhadas pelo código.

Evitar:

```ts
language = "Portuguese";
language = "PT";
language = "portugal";
```

quando a aplicação espera `pt`.

Utilizar um único sistema de códigos.

---

# 5. LANGUAGE METADATA

Manter metadados centralizados.

Exemplo conceptual:

```ts
{
  code: "pt",
  name: "Português",
  nativeName: "Português",
  flag: "????"
}
```

```ts
{
  code: "en",
  name: "English",
  nativeName: "English",
  flag: "????"
}
```

```ts
{
  code: "pl",
  name: "Polski",
  nativeName: "Polski",
  flag: "????"
}
```

Não duplicar esta informação em dezenas de componentes.

# 6. INITIAL LANDING PAGE

A landing page inicial deve estar sempre em inglês.

Antes da seleção de idioma:

* logo;
* descrição;
* funcionalidades;
* botão `Get Started`;
* instruções de instalação.

Depois da seleção:

o restante onboarding passa imediatamente para o idioma escolhido.

# 7. LANGUAGE SELECTION

Mostrar sempre:

???? Português
???? English
???? Polski

O utilizador deve compreender imediatamente qual idioma está a escolher.

Não mostrar apenas:

```text
PT
EN
PL
```

sem contexto visual quando existir espaço suficiente.

---

# 8. IMMEDIATE LANGUAGE SWITCH

Quando o utilizador seleciona um idioma:

1. atualizar estado;
2. persistir preferência;
3. atualizar UI;
4. atualizar textos;
5. atualizar mensagens de sistema;
6. manter dados do utilizador intactos.

A alteração de idioma não deve:

* apagar conversas;
* traduzir automaticamente dados persistidos;
* alterar mensagens originais;
* alterar nome do utilizador;
* alterar configurações de comunicação.

---

# 9. PERSISTENCE

A preferência de idioma deve persistir.

Ao reabrir a aplicação:

```text
interfaceLanguage
myLanguage
otherLanguage
```

devem ser recuperados corretamente.

Se o utilizador tiver dispositivos ligados, a preferência que deve ser sincronizada deve seguir as regras definidas pelo Architect.

Não assumir automaticamente que todas as preferências devem ser globais se a arquitetura definir preferências por dispositivo.

---

# 10. COMPLETUDE DAS TRADUÇÕES

Nunca considerar um idioma concluído enquanto existirem textos hardcoded sem justificação.

Evitar:

```tsx
<button>Enviar</button>
```

Preferir:

```tsx
<button>{t("chat.send")}</button>
```

Todos os textos de interface devem passar pelo sistema i18n.

Exceções legítimas:

* conteúdo escrito pelo utilizador;
* nomes próprios;
* nomes de ficheiros;
* conteúdo externo;
* texto que pertence explicitamente ao conteúdo original.

---

# 11. NÃO MISTURAR IDIOMAS

Não permitir interfaces como:

```text
Settings
Definições
Notifications
Traduzir
Save
```

ao mesmo tempo.

Exceto quando o texto faz parte do conteúdo de uma mensagem ou documento.

O idioma da UI deve ser consistente.

---

# 12. PORTUGUÊS

O português do TranslatorX deve utilizar **Português Europeu (PT-PT)**.

Evitar vocabulário brasileiro quando houver alternativa natural em português europeu.

Exemplos:

Preferir:

```text
Ficheiros
Definições
Utilizador
Ecrã
Aplicação
Telemóvel
Computador
```

Evitar usar sistematicamente:

```text
Arquivos
Configurações
Usuário
Tela
Aplicativo
Celular
```

quando o contexto for PT-PT.

---

# 13. ENGLISH

O inglês deve ser:

* natural;
* moderno;
* claro;
* profissional;
* simples.

Evitar traduções literais estranhas.

Exemplo:

Não traduzir mecanicamente expressões portuguesas.

O objetivo é transmitir a mesma intenção em inglês natural.

---

# 14. POLISH

O polaco deve ser tratado como idioma completo.

Não utilizar:

* tradução parcial;
* placeholders;
* texto inglês;
* transliterações improvisadas.

Respeitar:

* gramática;
* casos gramaticais;
* concordância;
* género;
* formas naturais de interface.

Quando uma tradução contextual exigir conhecimento linguístico especializado, utilizar a capacidade adequada de tradução/IA em vez de inventar.

---

# 15. TRANSLATION ENGINE

O sistema de tradução deve suportar todas as combinações:

```text
PT ? EN
PT ? PL

EN ? PT
EN ? PL

PL ? PT
PL ? EN
```

Também deve conseguir lidar com:

```text
sourceLanguage === targetLanguage
```

Nesse caso, não deve executar tradução desnecessária.

---

# 16. LANGUAGE DETECTION

Quando a origem não for conhecida, o sistema pode detetar o idioma.

Exemplo:

```text
"Jestem studentem."
```

detetar:

```text
pl
```

Depois:

```text
sourceLanguage = pl
targetLanguage = pt
```

A deteção deve ser tratada como uma inferência.

Não assumir que é 100% correta.

Quando existir ambiguidade significativa, permitir confirmação.

---

# 17. MANUAL LANGUAGE SELECTION

O utilizador deve conseguir selecionar manualmente:

```text
From:
???? Português

To:
???? Polski
```

A seleção manual deve ter prioridade sobre uma deteção automática quando o utilizador explicitamente escolhe o idioma.

---

# 18. AUTO TRANSLATION

Deve existir opção:

```text
Automatic translation
```

ou equivalente localizado.

Estados:

```text
ON
OFF
```

Quando OFF:

* manter mensagem original;
* permitir tradução manual.

Quando ON:

* aplicar tradução conforme configuração;
* manter sempre o original disponível.

---

# 19. ORIGINAL CONTENT MUST NEVER BE LOST

Esta é uma regra crítica.

Se o utilizador escrever:

```text
I can't come tomorrow because I'm sick.
```

o sistema pode produzir:

```text
Não posso ir amanhã porque estou doente.
```

Mas nunca deve substituir permanentemente o original.

Devem existir, quando aplicável:

```text
original
corrected
translated
```

---

# 20. CORREÇÃO VS TRADUÇÃO

São operações diferentes.

## Correção

Corrigir:

* ortografia;
* gramática;
* pontuação;
* erros evidentes.

## Tradução

Converter o conteúdo para outro idioma.

Fluxo conceptual:

```text
Original
?
Correção opcional
?
Tradução
```

Não confundir as duas operações.

---

# 21. PRESERVAÇÃO DE INTENÇÃO

A IA deve preservar:

* intenção;
* significado;
* contexto;
* tom;
* nível de formalidade;
* urgência;
* negação;
* números;
* datas;
* nomes;
* instruções.

Não transformar:

```text
Can you send this tomorrow?
```

em algo com significado diferente.

---

# 22. NÃO SOBRE-FORMALIZAR

Se o utilizador escrever:

```text
hey can u send me the file?
```

não transformar automaticamente em:

```text
Dear Sir/Madam, could you kindly provide the requested document at your earliest convenience?
```

A tradução deve preservar o nível de informalidade.

---

# 23. CONTEXTO

Tradução isolada pode ser ambígua.

O sistema deve utilizar contexto disponível quando autorizado.

Exemplo:

Mensagem:

```text
Can you do it?
```

Se o contexto indicar que `it` corresponde a um documento, a tradução deve considerar esse contexto.

Mas nunca inventar contexto inexistente.

---

# 24. CONVERSATION CONTEXT

Dentro de uma conversa, a IA pode utilizar:

* mensagens anteriores;
* idioma do remetente;
* idioma do destinatário;
* assunto da conversa;
* ficheiros relevantes autorizados.

O contexto deve ser limitado ao necessário.

Não enviar dados desnecessários para APIs externas.

---

# 25. AI TRANSLATION OUTPUT

Uma resposta de tradução estruturada pode seguir:

```ts
{
  sourceLanguage: "en",
  targetLanguage: "pl",
  original: "...",
  corrected: "...",
  translated: "...",
  confidence: 0.98
}
```

A arquitetura final deve seguir o contrato definido pelo Architect.

Não expor `confidence` ao utilizador se o valor não tiver significado fiável.

---

# 26. TRANSLATION ERROR HANDLING

Se a tradução falhar:

Não substituir o original.

Mostrar:

```text
Não foi possível traduzir esta mensagem.
Tentar novamente.
```

O original continua disponível.

Nunca mostrar:

```text
undefined
null
[object Object]
```

ao utilizador.

---

# 27. AI HALLUCINATION PREVENTION

A IA não deve inventar conteúdo.

Se uma expressão não for compreendida:

* preservar a expressão;
* indicar incerteza quando necessário;
* pedir contexto quando realmente necessário.

Não inventar:

* nomes;
* locais;
* datas;
* pessoas;
* significados;
* informações culturais.

---

# 28. NÚMEROS E DADOS

Ter especial atenção a:

* números;
* percentagens;
* preços;
* datas;
* horas;
* IDs;
* códigos;
* URLs;
* emails.

Nunca alterar:

```text
ID 01
```

para:

```text
ID 1
```

se a apresentação original exigir `01`.

Nunca alterar valores financeiros durante tradução.

---

# 29. NOMES PRÓPRIOS

Não traduzir automaticamente:

* nomes de pessoas;
* nomes de empresas;
* nomes de aplicações;
* IDs;
* usernames;
* URLs.

Exemplo:

```text
Samuel Lopes
TranslatorX
Ponto Digital
```

devem permanecer intactos salvo pedido explícito.

Opcionalmente:

# 31. COPY

O utilizador deve conseguir copiar:

* original;
* corrigido;
* traduzido.

Não copiar silenciosamente uma versão diferente daquela que o utilizador selecionou.

Exemplo:

# 38. CHAT IA CONTEXTUAL

Se o utilizador estiver numa conversa com um Monitor e disser:

```text

```

o sistema deve utilizar o contexto da mensagem selecionada/conversa, se disponível.

Não pedir novamente informações que já estejam claramente disponíveis.

# 39. SYSTEM TEXT TRANSLATION

Mensagens internas devem estar no i18n:

* enviado;
* entregue;
* lido;
* editado;
* eliminado;
* a traduzir;
* tradução concluída;
* erro;
* offline;
* sincronizando;
* ficheiro enviado;
* ficheiro recebido.

Nunca hardcodear estes textos.

---

# 40. NOTIFICATIONS

As notificações devem utilizar o idioma da interface configurado pelo utilizador.

Exemplo PT:

```text
?? Mensagem de Samuel Lopes - ID 01
```

EN:

```text
?? Message from Samuel Lopes - ID 01
```

PL:

```text
?? Wiadomo?? od Samuel Lopes - ID 01
```

O nome e ID não devem ser traduzidos.

---

# 41. DATE AND TIME LOCALIZATION

Datas e horas devem respeitar a localização quando apropriado.

Não traduzir manualmente nomes de meses.

Utilizar APIs de internacionalização adequadas:

```text
Intl.DateTimeFormat
Intl.NumberFormat
```

quando apropriado.

O timezone deve ser tratado separadamente do idioma.

Não assumir que:

```text
language = timezone
```

são a mesma coisa.

---

# 42. PLURALIZATION

Não criar frases manualmente como:

```text
1 messages
2 messages
```

Utilizar mecanismos de pluralização apropriados.

O polaco possui regras de pluralização diferentes do português e inglês.

Ter atenção especial a:

* 0;
* 1;
* 2;
* 5;
* números compostos.

---

# 43. GENDER

Não assumir género do utilizador sem informação.

Evitar frases que obriguem a escolher género quando isso não é necessário.

Quando uma língua exigir concordância:

* utilizar formulações neutras quando possível;
* utilizar dados explicitamente fornecidos quando necessário.

---

# 44. TEXT LENGTH

O layout deve suportar diferenças de comprimento.

Exemplo:

```text
English:
Settings

Portuguese:
Definições

Polish:
Ustawienia
```

Não criar componentes dependentes de uma determinada quantidade de caracteres.

---

---

# 46. PLACEHOLDERS

Quando utilizar parâmetros:

```text
messageFrom: "Mensagem de {{name}} - ID {{id}}"
```

Todos os idiomas devem possuir os mesmos placeholders.

Nunca traduzir o nome da variável.

Correto:

```text
{{name}}
{{id}}
```

Não:

```text
{{nome}}
{{identificador}}
```

num único idioma se o código espera os nomes originais.

---

# 47. MISSING TRANSLATIONS

Se uma key estiver em falta:

1. identificar;
2. registar;
3. corrigir.

Não mascarar silenciosamente o problema.

Durante desenvolvimento, pode existir fallback controlado.

Em produção, nenhuma key crítica deve faltar.

---

# 48. FALLBACK

A estratégia de fallback deve ser definida centralmente.

Exemplo:

```text
pl
?
en
```

ou outra definida pela arquitetura.

Não criar fallbacks diferentes em cada componente.

---

# 49. TRANSLATION CACHE

Quando apropriado, traduções repetidas podem ser reutilizadas.

Mas:

* não armazenar dados sensíveis desnecessariamente;
* respeitar privacidade;
* não misturar traduções entre utilizadores;
* considerar contexto;
* não reutilizar uma tradução contextual fora do contexto original sem validação.

---

# 50. API SECURITY

As APIs de tradução/IA não devem expor secrets no frontend.

Nunca colocar:

```text
API_KEY
SECRET
PRIVATE_TOKEN
```

diretamente em React.

Utilizar backend/Edge Functions conforme a arquitetura.

---

# 51. RATE LIMITING

Pedidos de tradução devem considerar:

* rate limiting;
* abuso;
* custos;
* tamanho máximo;
* frequência;
* erros repetidos.

Não permitir loops automáticos que consumam APIs indefinidamente.

---

# 52. PRIVACY

Texto enviado para serviços de IA/tradução deve respeitar as regras de privacidade do TranslatorX.

Enviar apenas o necessário.

Especial atenção a:

* conversas privadas;
* documentos;
* áudio;
* imagens;
* dados pessoais.

---

# 53. PERFORMANCE

Não traduzir novamente conteúdo que já possui tradução válida sem necessidade.

Evitar:

```text
render
? API
? tradução
? render
? API
? tradução
```

Criar fluxo previsível.

---

# 54. OFFLINE

Quando offline:

* interface continua disponível;
* conteúdos previamente disponíveis podem continuar visíveis;
* traduções que exigem API devem indicar indisponibilidade;
* pedidos podem aguardar sincronização apenas se essa funcionalidade tiver sido explicitamente implementada.

Nunca fingir que uma tradução foi concluída quando não foi.

# 61. DEFINITION OF DONE

O sistema de internacionalização está concluído quando:

* [ ] PT está completo;
* [ ] EN está completo;
* [ ] PL está completo;
* [ ] UI não mistura idiomas;
* [ ] onboarding está localizado;
* [ ] notificações estão localizadas;
* [ ] mensagens de sistema estão localizadas;
* [ ] tradução PT?EN funciona;
* [ ] tradução PT?PL funciona;
* [ ] tradução EN?PL funciona;
* [ ] original nunca é perdido;
* [ ] correção e tradução são operações distintas;
* [ ] contexto é respeitado;
* [ ] intenção é preservada;
* [ ] nomes/IDs não são traduzidos;

# 62. PRINCÍPIO FINAL

A internacionalização do TranslatorX não é apenas traduzir a interface.

É garantir que uma pessoa que fala português, inglês ou polaco tenha acesso à **mesma aplicação, com a mesma funcionalidade, o mesmo contexto e o mesmo significado**.

A regra central é:

> **Traduzir o conteúdo sem destruir o conteúdo original.**

E:

> **Melhor preservar uma expressão original do que inventar uma tradução incorreta.**

**Cada agente faz a sua especialidade, mas todos constroem o mesmo TranslatorX.**
