# 1. MISSÃO

Implementar e manter:

* conversas individuais;
* conversas de grupo;
* envio de mensagens;
* entrega;
* leitura;
* edição;
* eliminação;
* respostas;
* cópia;
* encaminhamento;
* tradução;
* reprodução de áudio;
* pesquisa;
* anexos;
* imagens;
* ficheiros;
* sincronização em tempo real;
* sincronização entre dispositivos;
* notificações relacionadas com mensagens.

Não inventar funcionalidades fora dos requisitos oficiais.

---

# 2. REGRAS FUNDAMENTAIS

O sistema deve respeitar estas regras:

1. Qualquer utilizador pode adicionar qualquer outro utilizador.
2. Não existe sistema de permissões entre Monitor e Aluno.
3. Um utilizador pode ter várias conversas.
4. Uma conversa pode ter 2 ou mais participantes.
5. Qualquer membro de um grupo pode adicionar/remover membros.
6. Qualquer membro pode enviar mensagens.
7. Qualquer membro pode editar/eliminar as suas mensagens conforme as regras definidas.
8. O original de uma mensagem nunca deve ser perdido silenciosamente.
9. Mensagens devem sincronizar entre dispositivos ligados.
10. O sistema deve funcionar corretamente com ligação instável.

---

# 3. TIPOS DE CONVERSA

Suportar:

### Individual

```text
User A ? User B
```

### Grupo

```text
User A
User B
User C
...
```

Não criar um tipo diferente apenas para Monitor/Aluno.

O papel do utilizador é um atributo do perfil, não uma limitação estrutural da conversa.

---

# 4. CRIAÇÃO DE CONVERSAS

Quando um utilizador adiciona outra pessoa:

1. procurar utilizador pelo ID;
2. validar que existe;
3. mostrar identificação;
4. permitir confirmar;
5. criar/abrir conversa.

Não utilizar o nome como identificador.

O identificador oficial é o ID único do utilizador.

---

# 5. DUPLICAÇÃO DE CONVERSAS

Para conversas individuais:

Não permitir que sejam criadas várias conversas independentes entre as mesmas duas pessoas sem uma razão funcional explícita.

Exemplo:

```text
User 01 ? User 02
```

deve abrir a conversa existente se ela já existir.

Para grupos:

cada grupo possui identificação própria.

---

# 6. GRUPOS

Um grupo deve possuir:

* ID;
* nome;
* avatar opcional;
* criador;
* participantes;
* data de criação;
* última atividade.

Os membros podem ser:

* Monitor;
* Aluno;
* qualquer outro utilizador permitido pelo produto.

Não criar hierarquia automática.

---

# 7. GESTÃO DE MEMBROS

Qualquer membro do grupo pode:

* adicionar pessoa;
* remover pessoa;
* visualizar participantes;
* consultar perfil básico.

Se a remoção de um membro tiver consequências importantes, mostrar confirmação.

Não permitir remover alguém silenciosamente.

---

# 8. GROUP MEMBER EVENTS

Alterações importantes podem gerar eventos no sistema:

```text
Samuel Lopes added João Silva
Maria left the group
Pedro was removed
```

Estes eventos devem ser localizados através do sistema i18n.

Não guardar estes eventos como se fossem mensagens normais quando a arquitetura definir um tipo próprio.

---

# 9. CHAT HEADER

O cabeçalho deve mostrar:

### Individual

* nome;
* ID;
* estado de ligação quando disponível;
* opções da conversa.

### Grupo

* nome;
* número de participantes;
* opções do grupo.

No mobile, evitar cabeçalhos demasiado altos.

Se a arquitetura utilizar outros tipos, respeitar o contrato definido.

# 13. ORIGINAL MESSAGE

Toda mensagem textual deve preservar o conteúdo original.

Exemplo:

```text
original_text:
"hey can u send the file?"
```

Mesmo que a IA produza:

```text
corrected_text:
"Hey, can you send the file?"
```

e:

```text
translated_text:
"Olá, podes enviar o ficheiro?"
```

o original continua disponível.

---

# 14. EDIT MESSAGE

O utilizador deve poder editar uma mensagem quando permitido pela regra do produto.

Ao editar:

* atualizar conteúdo editável;
* guardar `edited_at`;
* indicar visualmente `Edited`;
* preservar informação necessária para auditoria/contexto conforme a arquitetura.

Nunca transformar a mensagem numa nova mensagem sem necessidade.

---

# 15. EDITED INDICATOR

Uma mensagem editada deve mostrar:

```text
Edited
```

ou equivalente localizado.

O utilizador deve conseguir perceber que o conteúdo mudou.

---

# 16. DELETE MESSAGE

Suportar:

### Delete for me

Remove/oculta a mensagem apenas para o utilizador.

### Delete for everyone

Remove o conteúdo para os participantes quando autorizado.

Em vez de apagar silenciosamente o espaço da mensagem, preferir:

```text
This message was deleted.
```

ou equivalente localizado.

---

# 17. DELETED MESSAGE

Uma mensagem eliminada para todos deve manter estrutura suficiente para preservar:

* posição temporal;
* contexto da conversa;
* consistência do histórico.

Não mostrar o conteúdo original depois da eliminação quando a regra de produto exigir remoção.

---

# 18. MESSAGE STATUS

Cada mensagem deve poder ter estados:

```text
sent
delivered
read
```

Visualmente:

### Sent

Mensagem enviada pelo cliente.

### Delivered

Mensagem recebida pelo destinatário/dispositivo.

### Read

Mensagem visualizada.

Os estados devem ser atualizados através de eventos confiáveis.

Não marcar como lida simplesmente porque a mensagem chegou ao dispositivo.

---

# 19. READ STATE

Quando o utilizador abre uma conversa:

* determinar mensagens não lidas;
* marcar as relevantes como lidas;
* sincronizar estado;
* atualizar UI.

Evitar enviar milhares de requests individuais.

Utilizar operações eficientes/batch quando possível.

---

# 20. UNREAD COUNTER

Cada conversa pode apresentar:

```text
3
```

para indicar mensagens não lidas.

Ao abrir a conversa:

```text
3 ? 0
```

O contador deve sincronizar entre dispositivos.

---

# 21. DELIVERY STATE

A entrega deve ser distinguida da leitura.

Exemplo:

```text
Sent
Delivered
Read
```

Não assumir:

```text
delivered = read
```

---

# 22. OFFLINE MESSAGING

Se o produto suportar envio offline:

* guardar temporariamente;
* marcar como pending;
* sincronizar quando voltar online;
* resolver conflitos.

Se o envio offline ainda não estiver implementado:

mostrar claramente que a mensagem não foi enviada.

Nunca fingir sucesso.

---

# 23. CONNECTION STATES

A UI deve conseguir distinguir:

```text
Online
Offline
Connecting
Syncing
```

Não utilizar apenas um booleano.

---

# 24. REALTIME

Utilizar Supabase Realtime conforme definido pela arquitetura.

Eventos relevantes:

* nova mensagem;
* edição;
* eliminação;
* read state;
* delivery state;
* membro adicionado;
* membro removido;
* alteração de grupo.

Ao subscrever canais:

* limpar listeners;
* evitar duplicação;
* evitar memory leaks;
* desligar subscriptions quando a conversa sair de contexto.

---

# 25. DUPLICATE REALTIME EVENTS

O sistema deve ser idempotente.

Se o mesmo evento chegar duas vezes:

```text
message_id = abc
```

não criar duas mensagens.

Utilizar identificadores únicos e lógica de deduplicação adequada.

---

# 26. MESSAGE ORDERING

Mensagens devem aparecer pela ordem correta.

Utilizar timestamps e/ou ordenação definida pelo backend.

Não confiar apenas na ordem em que eventos Realtime chegam.

Uma mensagem atrasada pode chegar depois de uma mensagem mais recente.

---

# 27. PAGINATION

Conversas longas devem utilizar paginação.

Não carregar milhares de mensagens de uma vez.

Fluxo típico:

```text
Latest messages
?
Scroll up
?
Load older messages
```

Manter posição do scroll ao carregar mensagens antigas.

Não fazer o utilizador saltar para o fundo inesperadamente.

---

# 28. CHAT SCROLL

Quando receber nova mensagem:

### Se o utilizador estiver perto do fundo

fazer scroll para a nova mensagem.

### Se estiver a consultar mensagens antigas

não deslocar o utilizador.

Mostrar indicador:

```text
? 3 novas mensagens
```

ou equivalente.

---

# 29. REPLY

O utilizador pode responder a uma mensagem.

A resposta deve apresentar:

* referência visual à mensagem original;
* conteúdo resumido;
* autor;
* mensagem atual.

Ao clicar na referência:

* fazer scroll para a mensagem original, se disponível.

---

# 30. COPY

Ações de cópia devem permitir selecionar:

* original;
* corrigido;
* traduzido.

Copiar exatamente o conteúdo correspondente.

Não incluir metadata desnecessária.

---

# 31. FORWARD

O utilizador pode encaminhar uma mensagem.

Fluxo:

```text
Select message
?
Forward
?
Select conversation
?
Confirm
?
Send
```

Indicar visualmente que é uma mensagem encaminhada quando aplicável.

Preservar o conteúdo original conforme a política do produto.

---

# 32. SEARCH

Suportar pesquisa:

### Dentro da conversa

Pesquisar mensagens da conversa atual.

### Global

Pesquisar entre conversas quando a funcionalidade estiver disponível.

Pesquisar:

* conteúdo;
* nomes;
* IDs;
* ficheiros associados quando suportado.

Não pesquisar dados aos quais o utilizador não deveria ter acesso.

---

# 33. SEARCH RESULTS

Ao selecionar resultado:

* abrir conversa;
* fazer scroll até mensagem;
* destacar temporariamente resultado.

Não perder o contexto.

---

# 34. MESSAGE MENU

Cada mensagem deve ter menu contextual com:

* Responder;
* Traduzir;
* Copiar;
* Encaminhar;
* Editar;
* Eliminar;
* Ouvir.

Mostrar apenas ações válidas para aquela mensagem.

Exemplo:

Uma mensagem de outra pessoa não deve apresentar `Editar`.

---

# 35. TRANSLATION

A tradução deve seguir as regras do subagente:

`03_I18N_TRANSLATION.txt`

Nunca implementar uma segunda lógica de tradução independente.

O sistema de mensagens deve chamar o serviço de tradução comum.

---

# 36. AUTOMATIC TRANSLATION

Quando ativada:

```text
original
?
corrected
?
translated
```

A UI deve continuar a permitir visualizar o original.

Quando desativada:

* mostrar original;
* permitir tradução manual.

# 37. CONTEXTUAL AI

Se o utilizador selecionar uma mensagem e pedir:

```text

```

ou:

```text

```

o sistema deve passar à IA:

* mensagem selecionada;
* contexto mínimo necessário;
* idioma do utilizador;
* conversa quando necessário.

Não enviar a conversa inteira sem necessidade.

* progress;
* transcrição;

# 40. IMAGE MESSAGES

Suportar:

* preview;

* download;
* tradução OCR quando aplicável;
* explicação por IA quando aplicável.

# 41. FILE MESSAGES

Ficheiros enviados numa conversa devem aparecer como cards.

Mostrar:

* nome;
* tipo;
* tamanho;
* estado;
* ações.

Ações possíveis:

* abrir;
* download;
* traduzir;
* resumir;
* perguntar à IA.

# 42. ATTACHMENT UPLOAD

Durante upload:

mostrar:

```text
Uploading...
```

ou equivalente.

Se falhar:

```text
Upload failed
Try again
```

Não apresentar o ficheiro como enviado antes de existir confirmação adequada.

---

# 43. MESSAGE COMPOSER

O campo de mensagem deve suportar:

* texto;
* Enter para enviar conforme UX;
* Shift+Enter para nova linha em desktop quando apropriado;
* botão enviar;
* anexos;
* imagem;
* áudio;
* IA/tradução.

No mobile, o teclado não deve esconder o composer.

---

# 44. LONG MESSAGES

Mensagens longas devem ser legíveis.

Evitar:

* largura excessiva;
* linhas gigantes;
* overflow;
* texto cortado.

Suportar:

* links;
* quebras de linha;
* caracteres especiais;
* emojis.

---

# 45. LINKS

URLs nas mensagens devem ser tratadas cuidadosamente.

Podem ser convertidas em links clicáveis quando seguro.

Não executar automaticamente conteúdo externo.

A UI deve deixar claro que o utilizador está a sair da aplicação quando aplicável.

---

# 46. EMOJIS

Mensagens devem suportar emojis.

Não corromper:

* Unicode;
* emojis compostos;
* bandeiras;
* caracteres polacos;
* acentos portugueses.

---

# 47. MESSAGE TIMESTAMPS

Mostrar horários de forma localizada.

Utilizar o timezone correto do utilizador/dispositivo conforme arquitetura.

Não assumir que todos estão no mesmo timezone.

---

# 48. GROUP MESSAGE DISPLAY

Em grupos, cada mensagem recebida deve identificar o remetente.

Exemplo:

```text
Samuel Lopes
ID 01

Olá!
```

Não repetir o nome em cada mensagem consecutiva do mesmo utilizador quando isso prejudicar a UI.

Pode agrupar visualmente mensagens consecutivas.

---

# 49. GROUP CONTEXT

Quando o utilizador estiver num grupo:

A IA e tradução devem compreender que:

```text
speaker = sender
```

Não atribuir uma mensagem ao utilizador errado.

---

# 50. MEMBER SEARCH

Adicionar pessoas por ID.

Exemplo:

```text
Introduzir ID
[ 01 ]
```

ou:

```text
Introduzir ID
[ 100 ]
```

O sistema deve aceitar IDs com e sem zeros à esquerda quando a representação oficial permitir, mas deve normalizar internamente para o identificador correto.

---

# 51. INVALID ID

Se não existir:

```text

```

Não revelar informação adicional sobre IDs existentes ou inexistentes além do necessário para a funcionalidade.

---

# 52. USER PROFILE PREVIEW

Antes de adicionar alguém:

mostrar informação básica permitida:

* nome;
* ID;
* role, quando apropriado.

Não mostrar dados privados.

# 56. NOTIFICATIONS

Mensagens novas podem gerar notificações.

A notificação deve incluir:

* nome;
* ID;
* tipo de mensagem;
* contexto suficiente.

Exemplo:

```text
?? Mensagem de Samuel Lopes - ID 01
```

Ao clicar:

```text
notification
?
conversation
?
message
```

---

# 57. NOTIFICATION DUPLICATION

Evitar notificações duplicadas quando:

* vários eventos Realtime chegam;
* vários dispositivos estão ligados;
* uma mensagem é processada por mais de um worker.

A arquitetura deve garantir idempotência.

---

# 58. MULTI-DEVICE

Um utilizador pode ter:

* telemóvel;
* computador;
* outros dispositivos suportados.

Todos os dispositivos ligados ao mesmo perfil devem sincronizar:

* mensagens;
* estados;
* alterações;
* conversas;
* ficheiros;
* leitura;
* definições relevantes.

---

# 59. DEVICE REMOVAL

Quando um dispositivo é removido:

* revogar a ligação;
* interromper sincronização;
* invalidar sessão/canal quando aplicável;
* atualizar lista de dispositivos.

Não deixar um dispositivo revogado continuar a receber dados.

---

# 60. CONFLICTS

Possíveis conflitos:

* mensagem editada em dois dispositivos;
* mensagem eliminada enquanto está aberta;
* estado de leitura concorrente;
* alteração de grupo simultânea.

O backend deve ser a fonte de verdade.

O frontend deve reconciliar o estado em vez de simplesmente sobrescrever dados com estado local antigo.

---

# 61. SECURITY

Nunca confiar no frontend para decidir:

* quem pode enviar;
* quem pertence à conversa;
* quem pode eliminar;
* quem pode editar;
* quem pode ler.

Estas regras devem ser validadas no backend/database.

---

# 62. RLS

As políticas RLS devem garantir que um utilizador só consegue aceder às conversas e dados aos quais tem acesso.

Importante:

O projeto não deve assumir que o facto de não existir login tradicional significa que não existe necessidade de identidade segura.

A estratégia de identidade/sessão definida pelo Architect deve ser respeitada.

---

# 63. PRIVACY

Nunca colocar em logs:

* mensagens completas;
* ficheiros privados;
* tokens;
* dados sensíveis.

Logs devem conter apenas informação necessária para debugging.

---

# 64. RATE LIMITING

Controlar:

* spam;
* envio massivo;
* uploads;
* requests de tradução;
* chamadas de IA.

Não permitir que um cliente malicioso utilize o sistema sem limites.

---

# 65. MESSAGE VALIDATION

Validar no backend:

* conversation ID;
* sender identity;
* tamanho;
* tipo;
* conteúdo;
* attachments;
* relações.

Nunca confiar apenas na validação React.

---

# 66. XSS / CONTENT SECURITY

Mensagens são conteúdo não confiável.

Não renderizar HTML arbitrário enviado pelo utilizador.

Escapar/sanitizar conteúdo quando necessário.

Nunca executar:

* scripts;
* HTML perigoso;
* javascript URLs.

---

# 67. FILE SECURITY

Ficheiros enviados devem:

* utilizar Storage privado;
* respeitar permissões;
* possuir URLs temporárias quando necessário;
* validar MIME/type;
* limitar tamanho.

Nunca colocar ficheiros privados em URLs públicas permanentes sem necessidade.

# 75. DEFINITION OF DONE

O sistema de Messaging está concluído quando:

* [ ] conversas individuais funcionam;
* [ ] grupos funcionam;
* [ ] adicionar pessoa funciona;
* [ ] remover pessoa funciona;
* [ ] mensagens enviam;
