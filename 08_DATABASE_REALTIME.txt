# 2. PRINCÍPIO FUNDAMENTAL

A base de dados deve ser a **fonte de verdade** do TranslatorX.

Não confiar em:

* estado local do frontend;
* dados enviados pelo utilizador;
* IDs fornecidos pelo cliente;
* permissões calculadas apenas no frontend;
* flags locais para autorização.

O frontend apresenta o estado.

O backend e a base de dados validam o estado real.

Frontend:

React

Não introduzir outra base de dados sem necessidade arquitetural explícita.

---

# 4. DATABASE SOURCE OF TRUTH

Sempre que exista informação persistente importante:

guardar no backend.

Exemplos:

* utilizador;
* ID;
* conversas;
* mensagens;
* ficheiros;
* membros;
* dispositivos;
* pairing;
* notificações;
* consentimentos;
* configurações persistentes.

O localStorage pode ser utilizado para cache ou preferências locais, mas não deve ser a fonte de verdade de dados críticos.

---

# 5. USER IDENTITY

Cada utilizador possui:

```text
internal user identity
```

e:

```text
public numeric ID
```

Exemplo:

```text
01
02
03
...
09
10
11
...
100
```

O ID público:

* é único;
* nunca é reutilizado;
* não é o nome;
* não é uma password;
* não é um token;
* não deve ser utilizado como segredo.

---

# 6. SEQUENTIAL USER ID

A atribuição do ID deve ser realizada no backend.

Nunca fazer:

```text
SELECT MAX(id) + 1
```

no frontend.

Isso cria problemas de concorrência.

Utilizar mecanismo transacional seguro, como:

* PostgreSQL sequence;
* mecanismo de contador transacional;
* função SQL;
* outra solução backend-safe.

---

# 7. USER ID FORMAT

O sistema deve armazenar o valor de forma que a unicidade seja garantida.

A apresentação pode utilizar padding:

```text
1 ? 01
2 ? 02
9 ? 09
10 ? 10
100 ? 100
```

Não armazenar zeros como parte da lógica numérica se isso dificultar ordenação ou unicidade.

A camada de apresentação pode formatar o ID.

---

# 8. ID NEVER REUSED

Quando um utilizador for eliminado:

o ID público não deve voltar a ser atribuído.

A sequência deve continuar.

Exemplo:

```text
01
02
03
```

Se o utilizador `02` for eliminado:

```text
01
03
04
```

Nunca:

```text
01
02
03
```

com outro utilizador a reutilizar `02`.

---

# 9. USER PROFILE

Criar uma entidade equivalente a:

```text
user_profiles
```

Pode conter:

```text
id
auth_user_id
public_id
name
role
interface_language
my_language
other_language
created_at
updated_at
deleted_at
```

A estrutura final deve ser ajustada à arquitetura de autenticação escolhida.

---

# 10. ROLE

Os valores previstos são:

```text
student
monitor
```

A role é uma informação de perfil.

Não deve criar automaticamente uma hierarquia de permissões.

TranslatorX não possui:

```text
admin
super-admin
monitor-owner
```

como hierarquia funcional, salvo requisito futuro explícito.

---

# 11. NO HIERARCHY

Um monitor pode adicionar um aluno.

Um aluno pode adicionar um monitor.

Um utilizador pode criar grupos.

Os membros podem adicionar/remover pessoas de acordo com as regras do produto.

Mas o backend deve continuar a verificar se o utilizador possui acesso ao recurso específico.

---

# 12. AUTHENTICATION / IDENTITY

O TranslatorX não utiliza o tradicional:

```text
email + password
```

como fluxo principal de onboarding.

Por isso, a arquitetura deve definir uma identidade backend segura.

Possibilidades incluem:

* Supabase Auth apropriado;
* anonymous authentication com identidade persistente;
* sessão segura associada ao dispositivo/perfil;
* mecanismo equivalente suportado pela arquitetura.

Não inventar um sistema de autenticação inseguro baseado apenas em:

```text
public_id
```

ou:

```text
localStorage
```

---

# 13. AUTHORIZATION

Autenticação responde:

```text
Quem é o utilizador?
```

Autorização responde:

```text
O utilizador pode aceder a este recurso?
```

Nunca confundir os dois.

---

# 14. RLS

Quando os dados forem diretamente acessíveis pelo cliente através do Supabase:

utilizar RLS adequadamente.

Exemplos:

* utilizador pode ler o próprio perfil;
* utilizador pode ler conversas das quais é membro;
* utilizador pode ler mensagens de conversas das quais é membro;
* utilizador pode aceder a ficheiros autorizados.

---

# 15. RLS NÃO É A ÚNICA CAMADA

Num sistema sem login tradicional:

RLS sozinho não resolve automaticamente a identidade.

Antes de implementar policies:

garantir que existe uma identidade backend confiável.

Nunca fazer uma policy baseada simplesmente em dados fornecidos pelo cliente.

Exemplo inseguro:

```text
user_id = request.body.user_id
```

---

# 16. PRIVATE DATA

Dados privados devem possuir uma cadeia de autorização clara:

```text
Authenticated identity
?
Resource ownership/membership
?
Database policy
?
Data access
```

# 18. CONVERSATIONS

Uma entidade:

```text
conversations
```

deve representar:

* conversa individual;
* conversa de grupo.

Campos possíveis:

```text
id
type
title
created_by
created_at
updated_at
deleted_at
```

Tipos:

```text
direct
group
```

---

# 19. CONVERSATION MEMBERS

Utilizar uma relação:

```text
conversation_members
```

para associar utilizadores a conversas.

Campos possíveis:

```text
conversation_id
user_id
joined_at
last_read_at
```

Pode incluir metadata adicional quando necessário.

---

# 20. UNIQUE MEMBERSHIP

Um utilizador não deve aparecer duas vezes na mesma conversa.

Criar constraint equivalente a:

```text
UNIQUE(conversation_id, user_id)
```

---

# 21. DIRECT CONVERSATIONS

Uma conversa 1?1 deve possuir apenas dois membros.

O backend deve impedir duplicação acidental de conversas diretas quando a regra do produto exigir uma única conversa entre os mesmos utilizadores.

---

# 22. GROUP CONVERSATIONS

Grupos podem possuir:

```text
3+
```

membros.

Qualquer membro pode, conforme os requisitos do produto:

* adicionar;
* remover;
* enviar;
* editar;
* apagar;
* partilhar ficheiros.

A autorização final deve ser aplicada pelo backend.

---

```text
messages
```

Campos possíveis:

source_language
target_language
reply_to_message_id
created_at

A estrutura final deve ser coordenada com Messaging, AI e i18n.

---

# 24. MESSAGE TYPES

Suportar, conforme implementação:

```text
text
audio
image
file
system
```

Não criar tipos adicionais apenas para resolver problemas que poderiam ser tratados por metadata.

---

# 25. ORIGINAL CONTENT

Nunca substituir:

```text
original_text
```

pela tradução.

Quando necessário:

```text
original_text
+
corrected_text
+
translated_text
```

devem coexistir.

---

# 26. MESSAGE EDITING

Ao editar:

preservar informação suficiente para representar corretamente:

```text
edited_at
```

A interface deve conseguir mostrar:

```text
Edited
```

ou equivalente localizado.

---

# 27. MESSAGE DELETION

Suportar:

```text
delete for me
```

e:

```text
delete for everyone
```

A arquitetura deve distinguir entre:

* mensagem globalmente apagada;
* mensagem escondida apenas para um utilizador.

Não destruir informação globalmente quando o utilizador apenas escolheu “delete for me”.

---

# 28. DELETED MESSAGE

Quando uma mensagem for eliminada para todos:

a UI deve poder apresentar:

```text
This message was deleted
```

ou tradução equivalente.

O modelo deve permitir identificar que a mensagem existiu sem manter conteúdo privado desnecessário.

---

# 29. MESSAGE READ STATE

Utilizar mecanismos apropriados para:

```text
sent
delivered
read
```

Pode existir:

```text
message_reads
```

para representar leitura por utilizador.

---

# 30. GROUP READ STATUS

Em grupos:

uma única coluna:

```text
read_at
```

na mensagem pode não ser suficiente.

O estado de leitura deve ser modelado por membro quando necessário.

---

# 31. DELIVERY STATE

A entrega pode depender do dispositivo e da sincronização.

Não marcar como:

```text
delivered
```

apenas porque o servidor recebeu a mensagem.

Definir claramente:

```text
sent
```

vs:

```text
delivered
```

vs:

```text
read
```

---

# 32. MESSAGE ORDERING

Mensagens devem possuir ordenação determinística.

Não confiar exclusivamente em:

```text
timestamp
```

quando podem existir timestamps iguais.

Utilizar:

* ID ordenável;
* timestamp + ID;
* outra estratégia determinística.

---

# 33. TIMESTAMPS

Utilizar timestamps server-side sempre que possível.

Não confiar no relógio do dispositivo para informação crítica.

Armazenar timestamps de forma consistente, preferencialmente UTC.

A UI converte para o timezone local.

---

# 34. TIMEZONE

O backend deve trabalhar com timestamps consistentes.

A interface apresenta:

```text
hora local
```

de acordo com o dispositivo/configuração.

Não armazenar horários críticos como strings formatadas localmente.

---

# 35. PAGINATION

Mensagens e ficheiros não devem ser carregados todos de uma vez.

Utilizar:

* cursor pagination;
* range pagination;
* paginação baseada em ID/tempo.

Para chat, preferir carregamento incremental.

---

# 36. CHAT HISTORY

Ao abrir uma conversa:

carregar apenas uma janela inicial.

Ao fazer scroll para cima:

```text
load older messages
```

Evitar downloads gigantes.

---

# 37. REALTIME

Utilizar:

```text
Supabase Realtime
```

para eventos relevantes.

Exemplos:

```text
new message
message updated
message deleted
member added
member removed
file uploaded
notification created
device linked
```

---

# 38. REALTIME AUTHORIZATION

Nunca subscrever indiscriminadamente:

```text
all messages
```

do sistema.

O utilizador deve receber apenas eventos dos recursos aos quais tem acesso.

---

# 39. REALTIME CHANNELS

Organizar canais de forma controlada.

Exemplo conceptual:

```text
conversation:{conversationId}
```

O servidor deve garantir que o utilizador pode subscrever aquele recurso.

Não confiar apenas no nome do canal enviado pelo frontend.

---

# 40. REALTIME CLEANUP

Ao sair de uma página/conversa:

remover subscriptions quando apropriado.

Evitar:

```text
conversation 1 listener
conversation 2 listener
conversation 3 listener
...
```

ficarem ativos indefinidamente.

---

# 41. DUPLICATE EVENTS

Realtime pode produzir eventos que coincidam com alterações já refletidas localmente.

A aplicação deve conseguir lidar com:

```text
local optimistic update
+
Realtime event
```

sem duplicar mensagens ou ficheiros.

---

# 42. IDEMPOTENCY

Operações críticas devem possuir mecanismos de idempotência quando necessário.

Exemplo:

```text
Send message
```

Se o request for repetido:

não criar duas mensagens iguais por acidente.

Pode utilizar:

```text
client_message_id
```

ou mecanismo equivalente.

---

# 43. CONCURRENT UPDATES

Tratar concorrência em:

* edição;
* eliminação;
* membros;
* pairing;
* configurações;
* ID generation.

Não assumir que apenas um dispositivo pode alterar dados.

---

# 44. DEVICE PAIRING

O sistema deve suportar:

```text
Ligar computador
```

através de código aleatório de:

```text
6 dígitos
```

---

# 45. PAIRING CODE

O código:

* possui 6 dígitos;
* não deve duplicar entre códigos ativos;
* não expira segundo o requisito atual;
* não é password;
* não é o ID público do utilizador.

O backend deve garantir unicidade entre códigos ativos.

---

# 46. PAIRING SECURITY

Não armazenar o pairing code em plaintext se a arquitetura permitir hashing seguro.

Fluxo:

```text
Desktop requests pairing
?
Backend generates code
?
Phone enters code
?
Backend verifies
?
Devices linked
```

Não confiar apenas em comparação realizada no frontend.

---

# 47. PAIRING RACE CONDITIONS

Duas tentativas de utilizar o mesmo código devem ser tratadas corretamente.

A operação de consumo do código deve ser transacional.

---

# 48. PAIRING REUSE

Depois de um código ser utilizado:

definir explicitamente se:

* continua associado;
* é invalidado;
* pode ser reutilizado.

A implementação deve respeitar o comportamento definido pelo produto.

Não permitir associação acidental a outro perfil.

---

# 50. DEVICE REVOCATION

Quando o utilizador remover um dispositivo:

o backend deve revogar a associação.

O dispositivo removido não deve continuar a receber dados privados através da sessão antiga.

---

# 51. PUSH SUBSCRIPTIONS

---

# 52. MULTI-DEVICE SYNC

```text

+

```

Alterações devem sincronizar:

* mensagens;
* leituras;
* ficheiros;
* configurações;
* notificações;
* dispositivos.

# 61. AI REQUEST SECURITY

---

# 62. FILE DATABASE INTEGRATION

A entidade:

```text

```

deve relacionar-se corretamente com:

* owner;

---

# 63. MESSAGE-FILE RELATION

Um ficheiro enviado através de uma mensagem deve poder ser relacionado de forma explícita.

Evitar depender apenas de texto como:

```text
"document.pdf"
```

para descobrir o anexo.

---

# 64. FOREIGN KEYS

Utilizar foreign keys sempre que apropriado.

Exemplos:

```text
messages.conversation_id
? conversations.id
```

```text
messages.sender_id
? user_profiles.id
```

```text
conversation_members.user_id
? user_profiles.id
```

Isso protege a integridade referencial.

---

# 65. DELETE STRATEGY

Definir cuidadosamente:

```text
CASCADE
RESTRICT
SET NULL
```

Não utilizar `CASCADE` indiscriminadamente.

Antes de apagar:

avaliar impacto em:

* mensagens;
* ficheiros;
* notificações;
* dispositivos;
* histórico;
* consentimentos.

---

# 66. USER DELETION

Quando o utilizador solicitar:

```text
Eliminar todos os meus dados
```

o sistema deve conseguir tratar:

* perfil;
* conversas;
* mensagens;
* ficheiros;
* dispositivos;
* subscriptions;
* notificações;
* AI history;
* consentimentos conforme política;
* dados locais quando possível.

O processo deve ser seguro e consistente.

---

# 67. ID DELETION SAFETY

A eliminação de um utilizador nunca deve permitir reutilizar o `public_id`.

A sequência global deve continuar avançando.

---

# 68. DATABASE TRANSACTIONS

Utilizar transações quando várias alterações devem acontecer como uma única operação lógica.

Exemplo:

```text
Create conversation
+
Add members
```

ou:

```text
Pair device
+
Consume pairing code
```

---

# 69. ATOMIC OPERATIONS

Operações como:

```text
create message
+
attach file
```

devem possuir uma estratégia consistente para falhas parciais.

Não deixar:

```text
database says file exists
```

quando o ficheiro nunca chegou ao Storage.

---

# 70. STORAGE/DATABASE CONSISTENCY

Storage e PostgreSQL são sistemas diferentes.

Não assumir atomicidade automática entre ambos.

Definir fluxos de compensação para:

* upload falhado;
* metadata criada sem ficheiro;
* ficheiro criado sem metadata;
* delete incompleto.

---

# 71. INDEXES

Criar índices para queries reais.

Possíveis índices:

```text
user_profiles(public_id)
conversation_members(user_id)
conversation_members(conversation_id)
messages(conversation_id, created_at)
messages(sender_id)
files(owner_id, created_at)
notifications(user_id, created_at)
linked_devices(user_id)
```

Os índices finais devem ser baseados no uso real.

Não criar dezenas de índices sem necessidade.

---

# 72. UNIQUE CONSTRAINTS

Utilizar constraints para regras que devem ser impossíveis de violar.

Exemplos:

```text
public_id UNIQUE
```

```text
pairing_code UNIQUE
```

quando aplicável.

```text
conversation_id + user_id UNIQUE
```

---

# 73. CHECK CONSTRAINTS

Quando apropriado, utilizar:

```text
CHECK
```

para limitar valores inválidos.

Exemplo conceptual:

```text
role IN ('student', 'monitor')
```

---

# 74. ENUMS

Enums PostgreSQL podem ser utilizados quando proporcionarem estabilidade.

Mas não utilizar enums indiscriminadamente se o produto exigir alterações frequentes.

A escolha deve ser arquitetural.

---

# 75. NULLABILITY

Definir corretamente:

* obrigatório;
* opcional;
* nullable.

Não utilizar `NULL` indiscriminadamente para esconder estados indefinidos.

---

# 76. DATA NORMALIZATION

Evitar duplicar dados que podem ficar inconsistentes.

Exemplo:

Não armazenar o nome do utilizador permanentemente em todas as mensagens apenas para apresentação, salvo se existir uma razão explícita.

Referenciar o perfil quando apropriado.

---

# 77. DENORMALIZATION

Pode ser utilizada para performance quando justificada.

Qualquer duplicação deve possuir uma estratégia de sincronização.

Não duplicar dados apenas para tornar uma query ligeiramente mais simples.

---

# 78. SEARCH

Pesquisas de mensagens e ficheiros devem respeitar:

* utilizador;
* conversa;
* autorização.

Nunca criar uma pesquisa global que permita descobrir conteúdo privado.

---

# 79. MESSAGE SEARCH

Se o sistema permitir pesquisa de mensagens:

pesquisar apenas dentro das conversas autorizadas.

A query deve ser eficiente para grandes volumes.

---

# 80. FILE SEARCH

A pesquisa de ficheiros deve respeitar:

```text
owner
+
conversation access
```

quando o ficheiro estiver partilhado.

---

# 81. REALTIME PERFORMANCE

Não enviar eventos desnecessários.

Exemplo:

um utilizador não precisa de receber eventos de:

```text
Conversation X
```

se não pertence à conversa.

---

# 82. CONNECTION CLEANUP

O frontend deve libertar:

* Realtime channels;
* listeners;
* subscriptions;

quando deixam de ser necessários.

O Database Agent deve documentar o padrão recomendado.

---

# 83. OFFLINE / LOCAL CACHE

Pode existir cache local para:

* última conversa;
* mensagens recentes;
* perfil;
* configurações.

Mas:

```text
cache != source of truth
```

Ao recuperar conexão:

sincronizar com o servidor.

---

# 84. CONFLICT RESOLUTION

Definir comportamento para:

```text
Phone edits message
+
Desktop edits same message
```

Não assumir que conflitos nunca ocorrerão.

Utilizar:

* timestamps;
* version fields;
* optimistic concurrency;
* regras de last-write;
* ou outra estratégia definida pelo Architect.

---

# 85. OPTIMISTIC UPDATES

O frontend pode atualizar imediatamente:

```text
Mensagem enviada
```

antes da confirmação final.

Mas deve existir rollback quando o backend rejeitar.

---

# 86. SERVER ERRORS

Erros do backend devem ser previsíveis.

Utilizar códigos ou estados consistentes.

Não obrigar o frontend a interpretar mensagens SQL para perceber o erro.

---

# 87. API LAYER

Operações sensíveis podem utilizar:

```text
Supabase Edge Functions
```

em vez de permitir acesso direto ao PostgreSQL.

Especialmente para:

* pairing;
* user ID generation;
* operações administrativas internas;
* processamento;
* operações multi-step;
* ações com lógica complexa.

---

# 88. DATABASE FUNCTIONS

Functions PostgreSQL podem ser utilizadas quando:

* precisam de atomicidade;
* são pequenas;
* pertencem claramente à camada de dados.

Não colocar toda a lógica da aplicação dentro de SQL.

---

# 89. TRIGGERS

Triggers podem ser utilizados para:

* timestamps;
* integridade;
* eventos internos;

quando forem realmente apropriados.

Evitar triggers excessivos que tornem o sistema difícil de compreender.

---

# 90. MIGRATIONS

Todas as alterações estruturais devem ser realizadas através de migrations controladas.

Nunca editar produção manualmente sem registo da alteração.

Cada migration deve ser:

* versionada;
* reproduzível;
* testável.

---

# 91. MIGRATION SAFETY

Antes de migration:

verificar:

* tabelas existentes;
* dependências;
* foreign keys;
* RLS;
* índices;
* dados existentes.

Nunca destruir dados existentes sem requisito explícito.

---

# 92. SEED DATA

Não colocar dados fictícios em produção.

Durante desenvolvimento:

seeds podem existir quando necessários.

Devem estar claramente separados da produção.

---

# 93. ENVIRONMENT SEPARATION

Sempre que possível separar:

```text
development
staging
production
```

Não apontar desenvolvimento diretamente para dados reais.

---

# 94. BACKUPS

A infraestrutura deve possuir mecanismo de backup adequado.

Não assumir que uma eliminação pode ser revertida simplesmente porque existe Realtime.

Realtime não é backup.

---

# 95. DATA RETENTION

Definir políticas de retenção para:

* mensagens;
* ficheiros;
* notificações;
* AI requests;
* pairing;
* logs;
* dados apagados.

Não eliminar automaticamente dados sem uma política definida.

---

# 96. PRIVACY

Minimizar:

* dados armazenados;
* logs;
* metadata desnecessária;
* conteúdo duplicado.

Dados privados devem estar protegidos por autorização adequada.

---

# 97. LOGGING

Logs técnicos podem incluir:

* request ID;
* operação;
* status;
* duração;
* erro técnico.

Não incluir desnecessariamente:

* mensagens completas;
* documentos;
* áudio;
* imagens;
* tokens;
* API keys.

---

# 98. RATE LIMITING

Operações sensíveis devem possuir proteção contra abuso.

Exemplos:

* criação de pairing;
* tentativa de pairing;
* envio de mensagens;
* uploads;
* AI requests;
* criação de conversas.

Os limites devem ser implementados no backend.

# 116. PRINCÍPIO FINAL

A base de dados do TranslatorX deve ser:

```text
Consistente
+
Segura
+
Relacional
+
Escalável
+
Sincronizada
+
Auditável tecnicamente
```

O frontend nunca deve ser considerado uma autoridade de segurança.

O ID público nunca é uma credencial.

O Realtime nunca substitui autorização.

O Storage nunca substitui ownership.

O cache nunca substitui a base de dados.

E:

> **Toda operação crítica deve ser segura mesmo que o frontend seja manipulado.**

**Cada agente faz a sua especialidade, mas todos constroem o mesmo TranslatorX.**
